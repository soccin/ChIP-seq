## 0. Summary

Three parts, one release (`v1.0.0`, breaking: Slurm only, counts change, names change):

1. **Port to IRIS/Slurm**, following the ATAC-seq model exactly (v1.5.1 plus the
   fixes on its `devs` branch): control job
   under `~/bin/sbatch`, stages through the `~/bin/bsub` shim, `bSync`/`bCheck`
   sequencing, `00.RUNSTATUS.txt` + `SLURM.CTRL/jobs.tsv` + `#CHIP_EXIT` trailer,
   `bin/checkRun.sh`, walltime classes, `/localscratch` temp files. The JUNO/LSF
   path is removed, not kept.
2. **featureCounts fix.** The bug in this repo is **not** the one in the ATAC brief.
   This repo vendors featureCounts **v2.0.6** (since v0.7.0, 2024-05-04), and
   `pipe.sh` calls it with `-p` but without `--countReadPairs`. In 2.0.2 and later
   `-p` only declares the input paired, so every ChIP run since v0.7.0 has counted
   **reads, not fragments**, in **every** column. This is exactly the "biggest trap"
   the ATAC brief warns about (its section 6.2 item 1), already live here for two
   and a half years. Confirmed on all three ChIP runs visible on IRIS (section 2.2).
   The fix is the same as ATAC's: featureCounts 2.1.1 with `-p --countReadPairs`,
   plus Check A (pairing) and Check B (independent count), so counts are never
   accepted unchecked again. ATAC has built and validated the three scripts on
   its `devs` branch; this repo copies them and adds a single-end mode.

3. **Genome builds and loose behavior.** A genome is named by its build tag
   (`b37`, `hg38`, `mm10`) everywhere, and every genome-dependent value comes
   from one table; any other name is an error (section 3.6). Errors exit
   non-zero, names are matched exactly, the run checks what the user tells it
   against the data, and nothing depends on a personal `~/.Rprofile`
   (section 3.7).

All three land in the same release because the Count stage is rewritten
once (`bin/countPeaks.sh`) and validated once, and because every later
change to names or arguments would break runs made in between.

## 2. Findings

### 2.1 The featureCounts history of this repo

| Period | Binary | Where | Evidence |
| --- | --- | --- | --- |
| 2018-03-04 (`832fd27`) to 2024-05-04 | subread **1.6.0** | repo root `featureCounts` | `git show d2100c2^:featureCounts \| strings` contains `subread-1.6.0-Linux-x86_64`. Same era and version as the ATAC binary (md5 `3be999ae...`). |
| 2024-05-04 (`30e36f6`, v0.7.0) to now | subread **2.0.6** | `bin/featureCounts` | `bin/featureCounts -v` prints `featureCounts v2.0.6`; md5 `7b698d64c6e4e3e04addd3d56361e12d`, 2,723,888 bytes, **dynamically linked**; `docs/install.md` points at the 2.0.6 source tarball. |

`pipe.sh` lines 256 to 260 have not changed across the upgrade:

```
$SDIR/bin/featureCounts -O -Q 10 -p -T 10 -F SAF -a ... -o ... $PBAMS
```

The 2.0.6 help text in the vendored binary says it plainly: "`-p` ... libraries are
assumed to contain paired-end reads. ... the 'countReadPairs' parameter controls if
read pairs or reads should be counted." Without it, reads are counted.

So this repo has had two different counting defects in sequence:

- **2018 to 2024-05 (1.6.0):** possibly the ATAC race (one BAM occasionally
  unpaired, that column about 2x). Not reproducible here: no run from that period
  with a count summary survives on `/data1` (section 2.3). Runs are on dead `/juno`
  paths or were never copied.
- **2024-05 to now (2.0.6, no `--countReadPairs`):** every column is read-counted,
  deterministically. No race, no sample-to-sample variation.

### 2.2 Evidence: every 2.0.6 run counted reads

For each run, the per-sample sum of all rows of `peaks_raw_fcCounts.txt.summary`
("Total" in featureCounts terms) against mapped reads from `samtools idxstats` on
the postProcess BAM in `out/bam/`. A fragment count would be half the mapped reads
(the postProcess BAM holds proper pairs only, so pairs = mapped/2 exactly).

| Run | Date | Version (`cmd.sh.log`) | Genome | Samples | Summary total vs mapped reads |
| --- | --- | --- | --- | --- | --- |
| `00.JUNO/ThompsonC/NgC3/Proj_16852` | 2025-01-26 | v0.7.2-4-g802de80 | mm10 | 8 (Cut&Run, IgG controls) | **equal, all 8** (e.g. Cyc_1 53,589,518 = 53,589,518) |
| `KentsisA/AntonoA/Proj_15235/ChIPSeq` | 2025-04-01 | v0.7.2-6-gddb4ce8 | mm10 | 2 | **equal, both** |
| `KentsisA/YamadaM/Proj_15235_B/ChIP` | 2026-07-19 | v0.9.0-0-g8b713b2 | mm10 | 4 | **equal, all 4** |

Ratio to true pairs is 2.000 in every column of every run. The ATAC brief's Check A
(fail outside 0.95 to 1.05) would have failed all three runs.

Affected outputs in those runs: `peaks_raw_fcCounts.txt` and `.summary`,
`scaleFactorsDESeq2.csv`, the `qcChIPSeq_*.pdf` pages built from the matrix (the
bar charts labelled "Mapped Reads in MACS Peaks" show reads, which is what the label
says, but the matrix behind the PCA is read counts), and any `diffAnalysisPairwise.R`
run on the matrix (Proj_15235_B has a `ChIPAnalysis/` directory built on the summary).

How wrong, compared with the ATAC case: the doubling is near uniform across
samples, so DESeq2 size factors move little (a fragment with both mates in a peak
counts 2 instead of 1, one with one mate in a peak counts 1 either way; per-sample
read/fragment ratios are close but not equal). edgeR tests on doubled counts have
understated variance and overstated significance. BigWigs, MACS peaks and the atlas
are not affected. Remediation of these three runs is a separate decision `[D7]`;
it is not part of the code fix.

### 2.5 Pre-existing defects that the port will expose

Under LSF these were masked. Under `set -o pipefail` and `bCheck` they would fail
the run, or they are needed for the run-status machinery to be truthful.

- `callPeaks_ChIPseq.sh`: `MACS_ERROR=$?` after `set -e` is always 0 (`01.TODO.md`
  #3); calls an undefined `usage`; `exit -1`.
- `makeBigWigFromBEDZ.sh`: the `macs2 predictd ... | tee` pipeline masks a predictd
  failure (no `pipefail`). Under `pipefail` a control sample on which predictd
  cannot build a model would fail the BW job and the run. `[D11]`
- `makeBigWigFromBEDZ.sh`: with three arguments `scaleFactor=$2` is the BED path
  (same bug as ATAC `00.ISSUES.md` #5). `pipe.sh` never passes three.
- `pipe.sh`: `set -eu` plus `case $1` in the option loop: a command line that ends
  on an option (no BAM) hits an unbound `$1`. Genome is detected from the first BAM
  only. `exit -1`.
- `postMapBamProcessing_ChIPSeq_NoPP.sh` and `_SE.sh` have **no** `set -e` and no
  `module load samtools`; they inherit the environment of the control job.
- `generateMACSArgs.R` has no `## START/END` tracing and its exit status is checked
  by `pipe.sh` with `$?` after `set -e` (dead check, same pattern as above).
- `getMedianFragmentLengthFromPredictDFile.R` prints `NA` if no log has an estimate;
  `pipe.sh` passes that straight to MACS as `--extsize NA`.
- `annotateWithHomer.sh` prepends `chr` to every line of the peak file. MACS peak
  files from mm10 BAMs already start with `chr1` (checked: Proj_15235_B
  `*_peaks.broadPeak`), so HOMER receives `chrchr1` and annotates nothing. The
  prefix is only right for b37 BAMs, whose contigs are `1`, `2`, ... `[D5]`
- `generateMACSArgs.R`: a control in the pairing file that matches no BAM silently
  becomes `_NoCTRL`, so a typo in column 1 runs that target without a control and
  nothing says so. A target that matches more than one BAM gets the message "Can
  not find target sample", not the degenerate-match one. `[D15]`
- `pipe.sh` writes `out/pipeline_info/cmd.sh.log` only at the end of a run with a
  pairing file; the no-pairing path exits before it.
- `postPipe.sh` moves `out/*.ba?` to `out/bam/` and `out/*.bed.gz` to `out/bed/`.
  After that the BAM paths in the count summary header no longer exist, the
  absolute `.bam.bai` symlinks break, and Check A cannot find the BAMs of a
  finished run (section 4.3).
- `annotateWithHomer.sh` passes `hg19` to `annotatePeaks.pl` unconditionally, while
  all three audited IRIS projects are mm10. It also has a broken shebang
  (`#/bin/bash`) and never deletes its temp file (`echo rm $TMPFILE`). `[D5]`
- Errors that exit 0: `R/diffAnalysisPairwise.R:59,199` and `qc_ChIPSeq_02.R:4`
  end with `quit()`, so an unknown genome in the differential analysis
  "succeeds"; the usage paths of `pipe.sh`, `postPipe.sh`, `callPeaks_ChIPseq.sh`,
  `getGenomeBuildBAM.sh`, `annotateWithHomer.sh`, `deliverResults.sh` and
  `bin/picardV2` end with a bare `exit`.
- Genome choices are spread over five mechanisms that can disagree: two `case`
  statements with an `mm10*` glob (`callPeaks_ChIPseq.sh:38`,
  `makeBigWigFromBEDZ.sh:27`), which also accepts `mm10_hBRAF_V600E` and fails
  later for lack of a genome file; an `@SQ` regex in all three POST scripts
  (`postMapBamProcessing_ChIPSeq.sh:24-31` and copies); a per-line `chr` rule in
  `annotateWithHomer.sh`; a first-row `chr` check in
  `R/diffAnalysisPairwise.R:386`; and the user typing `human` or `mouse`, which
  nothing checks against the data.
- `lib/genomes/` is inconsistent: `b37.genome` lists all 85 b37 contigs
  (including `MT` and the `GL` contigs), `mm10.genome` lists 22 (including
  `chrM`), `mm10+b37.genome` and `mouse_mm10.genome` are copies of
  `mm10.genome`, and `mouse_mm10.genome.bed` is not used.
- Sample names are recovered from file paths three different ways, each built
  for a different naming convention: the unanchored regex `<name>_.*postProcess`
  in `generateMACSArgs.R` (BIC `Proj_X_s_NAME`, PEMapper `NAME___MD`), and
  substitutions in `qc_ChIPSeq_02.R:38-40` and `R/diffAnalysisPairwise.R:70-100`.
  A name that is a prefix of another, or that contains a regex character,
  matches the wrong file or several.
- `-s|--single-end-on` is not checked against the BAMs. Paired BAMs run with
  `-s` go through the SE recipe and are counted as reads, and Check A in its
  single-end mode would pass them.
- The R scripts need `len()`, `cc()`, `DATE()` and, under this spec, `getSDIR()`
  from the user's `~/.Rprofile`. Run by another user, or after that file
  changes, they fail or change.

## 3. Part 1: the IRIS/Slurm port

### 3.1 Strategy

Same as ATAC-seq v1.5.1 plus the fixes now on ATAC `devs` (`docs/SLURM_PORT.md`, "Keep the control job, swap the three
primitives"). This pipeline has the same shape as ATAC's `pipe.sh` had (synchronous
driver, `xargs -n N bsub`, `bSync`), so the ATAC code transfers almost line for line.
PEMapper's dependency-graph rebuild is **not** the model here; the `-w post_done()`
chain for stages 4-6 becomes `bSync` sequencing, as it did in ATAC.

Copied from ATAC-seq `devs` at `28978c9` into `bin/` with the `ATAC` prefix renamed
to `CHIP` (variables, trailer, defaults), otherwise unchanged. Record the source
commit in `CLAUDE.md` and diff again when ATAC releases v2.0.0:

### 3.2 `pipe.sh`

Rewritten on the ATAC `pipe.sh` skeleton. Kept: the ChIP options
(`--pairing-file`, `-n|--narrow-peaks`, `--proper-pair-off`, `-s|--single-end-on`),
the stage order, the output layout (flat `out/`, `out/profiles`, `out/macs`), the
no-pairing-file behavior, `out/pipeline_info/cmd.sh.log`.

**Header and setup**

- `#SBATCH -p cmobic_cpu`, `--qos=priority`, `-t 3-00:00:00`, `-c 2`, `--mem=16G`,
  `-J CTRL.ChIP`, `-o SLURM.CTRL/%j.out`. Submit with `~/bin/sbatch`.
- `SDIR=${SBATCH_SCRIPT_DIR:-$(dirname $0)}`; fatal if `postMapBamProcessing_ChIPSeq.sh`
  is not there.
- `source bin/loadTools.sh; source bin/slurmTools.sh`; venv check (message points at
  `00.SETUP.sh`); `export PATH=$SDIR/bin:$PATH` stays. The POST scripts call
  `picardV2` by bare name and rely on that PATH reaching the stage job; change them
  to `$SDIR/bin/picardV2`.
- Option parsing in the ATAC `POSITIONAL_ARGS` style, so `set -u` cannot trip on `$1`.
- `-o|--outdir`: **remove** `[D2]` (decided), because every post-pipeline stage
  hardcodes `out/` (`01.TODO.md` #1), one run per directory makes it pointless, and
  removing it closes the TODO. If kept, it has to be threaded into three R scripts
  and `postPipe.sh`.
- `TAG=qChIP-Seq`; job names `${TAG}_<STAGE>_$$`; `CHIP_START` exported; `RUNRE`.
- Run records exactly as ATAC: `00.RUNSTATUS.txt` (`STATUS`, `STAGE`, `RC`, `MESSAGE`,
  `STARTED`, `FINISHED`, `VERSION`, `CTRL_JOBID`, `CTRL_LOG`, `HOST`, `PID`,
  `CHIP_START`, `GENOME`, `PEAK_TYPE`, `PROPER_PAIR`, `SE`, `PAIRS`, `FRAGLEN`,
  `SAMPLES`, `BAMS`, `JOBS`), `SLURM.CTRL/jobs.tsv`, `setStage`, `writeRunStatus`,
  `onExit` trap with `bKill` and `failedJobsMessage` for `MESSAGE`, `onSignal` for
  TERM/INT.
- `checkPreviousRun`: refuse if `00.RUNSTATUS.txt`, `SLURM.CTRL/jobs.tsv`, `out/`
  or `00_PIPE_DONE` exists. No rerun or resume logic (ATAC decision #6/#23 applies;

### 3.6 Genome builds

Rules (the user's direction, 2026-10-11):

1. A genome is named by its build tag, everywhere: run records, file names, and
   every argument. Supported tags: `b37` (GRCh37 with contigs `1`..`22`, `X`,
   `Y`, `MT`; the Broad's name), `hg38` (GRCh38 with `chr` contigs; the name
   the Broad and UCSC use) and `mm10` (GRCm38 with UCSC `chr` contigs). Species
   words (`human`, `mouse`) and stand-in names (`hg19` for b37 data) are not
   accepted anywhere. Anything else is an error that lists the supported tags
   and exits non-zero.
2. Nobody types the genome of a run's own data. `pipe.sh` detects it from the
   BAM headers and records it; post-run tools read it from
   `00.RUNSTATUS.txt` and take no genome argument `[D16]`.
3. One table, `lib/genomes/GENOMES.tsv`, holds every genome-dependent value. A
   supported genome is a row of it. Shell scripts read it through
   `bin/genomeInfo.sh TAG FIELD`, which exits 1 for an unknown tag or field; R
   scripts through a `genomeInfo()` function in `tools.R`. No `case` on genome
   names and no globs such as `mm10*` remain in the stage scripts.
4. `lib/genomes/<TAG>.genome` lists exactly the contigs analyzed: autosomes,
   `X` and `Y`, with no mitochondria and no unplaced, random, decoy or viral
   contigs (b37 24, hg38 24, mm10 21). It is the POST region set
   (`samtools view -L` with the 3-column BED `contig 0 length` written from
   it; samtools reads the 2-column file as `contig position`, one base per
   line) and the chromosome sizes for `bedtools` and
   `wigToBigWig`. The new files are the first 24 lines of today's
   `b37.genome`, the first 21 of `mm10.genome`, and ATAC's `human_b38.genome`
   (24 lines). All three were checked 2026-10-11 against the IRIS reference
   dicts (`H.sapiens/b37`, `H.sapiens/GRCh38.d1.vd1`, `M.musculus/mm10`): same
   names, same lengths. `mm10+b37.genome`, `mouse_mm10.genome` and
   `mouse_mm10.genome.bed` go to `attic/` `[D17]`.
5. `pipe.sh` checks, before submitting anything, that every BAM header contains
   every contig of `<TAG>.genome` with the same length. This catches a header
   md5 mapped to the wrong tag and a genome file that does not match the data.
6. The rules for external resources are per tag, in the table, not guessed per
   file or per line: `chr` is added to b37 peaks before HOMER and ChIPseeker,
   and to no other build.

Unsupported on purpose: `mm10+b37` `[D17]` (no IRIS reference produces it, and
what the pipeline did with its human contigs was never checked) and
`hg38+mm39` (a PDX design question: which species a run analyzes). Both become
open issues.

### 3.7 Reliability rules

The featureCounts bug ran for two and a half years because nothing compared the
counts with anything. These rules apply to every script in v1.0.0; the static
checks in section 6 enforce the ones that can be found with `grep`.

1. **Errors exit non-zero, with a message that names the cause.** `exit 1`,
   `quit(status = 1)` or `stop()`; printing usage because the arguments are
   wrong is an error too. No bare `exit` or `quit()` in an error path.
2. **No silent fallback.** A missing input, an unmatched name, a missing
   fragment length, an unknown genome or a failed check stops the run. Already
   decided for predictd `[D11]`, the pairing file `[D15]`, `FRAGLEN` (stage 2b)
   and the counts (Checks A and B).
3. **Names are matched exactly.** Samples by `SM` tag, pairing and manifest
   entries by string equality `[D19]`, genomes by tag. No regex or prefix
   matching on names.
4. **The run detects what it can and checks what it is told.** Genome and
   sample names come from the BAMs. Options that describe the data are checked
   against it: `-s` must agree with the BAMs' paired flag. Post-run tools read
   the run record instead of asking again `[D16]`.
5. **Results are checked before use.** Count checks A and B; the deliverables
   check before `COMPLETED`; `postPipe.sh` refuses a run that `checkRun.sh`
   does not pass; the peak-contig check in `annotateWithHomer.sh`.
6. **No dependence on personal configuration.** The R scripts define or avoid
   what they use (`length()`, `str_c()`, `format(Sys.Date(), "%Y%m%d")`, the
   script directory from `commandArgs()`), and `pipe.sh` and `postPipe.sh` run
   R with `Rscript --no-init-file` `[D20]`. Shared infrastructure (`~/bin`
   wrappers, HOMER, the R library) is listed in `CLAUDE.md` with versions.
7. **Every run records what it used**: genome, samples, options, pairs,
   fragment length, tool versions and the pipeline version with `--dirty`.

### 4.2 `bin/countPeaks.sh` (the Count stage, from ATAC)

ATAC's script, with one addition:

```
countPeaks.sh [--single-end] MAPQ SAF OUT BAM...
```

- Paired-end (default), as ATAC: `featureCounts -O -Q $MAPQ -p --countReadPairs
  -T $SLURM_CPUS_PER_TASK --tmpDir "$TMPDIR" -F SAF -a SAF -o OUT BAM...`, then
  Check A on `OUT.summary`; exit 1 if either fails. Defaults as today: no `-B`
  (singletons count; there are none after the default ENCODE filter), no `-C`
  (chimeric pairs count; relevant only to `--proper-pair-off` runs), multimappers
  not counted.
- `--single-end` (new; `pipe.sh` passes it when `SE=Yes`): the same without `-p`
  and `--countReadPairs`, and Check A in single-end mode.
- `MAPQ` is 10, as today, for comparability. It is a no-op: the postProcess BAM is
  already filtered at MAPQ 30.
- Threads come from the job's CPUs (`-n 8`, as ATAC) `[D14]`.
- On failure the run ends `STATUS=FAILED STAGE=Count`, and `failedJobsMessage`
  (ATAC `fix/message`) puts the Check A line into `MESSAGE`, as ATAC test20 showed.

### 4.3 Check A: `bin/checkCounts.sh [--single-end] SUMMARY [ASSIGNED ...]`

ATAC's script: Check A always, Check B when given the `assignedCheck.sh` results.
One line per sample and check in every case, so the log records the numbers.
Two additions, marked "new" below:

- For each BAM column: `frag` is the sum of all rows of the column, and `mapped` is
  the sum of column 3 of `samtools idxstats BAM`. Paired-end: `ratio = frag /
  (mapped / 2)`, band 0.95 to 1.05 `[D12]`. ATAC measured 1.000 to 1.004 on correct
  counts; the excess is singletons whose mate failed the MAPQ filter. The old 2.0.6
  runs here give 2.000 in every column.
- `--single-end` (new): `ratio = frag / mapped`, same band.
- BAM fallback (new): if a BAM path in the summary header does not exist and
  `out/bam/<basename>` does, use that and say so. `postPipe.sh` moves the BAMs
  there, so without this a finished run cannot be audited.
- The `.bai` exists already: all three POST variants run picard `SortSam
  CREATE_INDEX=true`, so no Index stage is needed (ATAC has one). `idxstats`
  accepts `X.bai` or `X.bam.bai`.
- Standalone use: `ChIP-seq/bin/checkCounts.sh out/macs/peaks_raw_fcCounts.txt.summary`
  from an analysis directory audits an earlier run, including the three in
  section 2.2.

Neither addition changes ATAC's behavior: ATAC has no `out/bam/` and no
single-end mode. Offer both back so the two copies stay identical `[D1]`.

### 4.4 Check B: `bin/assignedCheck.sh BAM SAF OUT` (from ATAC, unchanged)

Per BAM: convert the SAF to BED (`Start - 1`), count the distinct read names
among the reads `samtools view -L` reports, and write `BAM<TAB>N` to OUT.
`checkCounts.sh` requires N to equal the `Assigned` row exactly. ATAC found
them equal on all 12 full-size and all 11 downsampled BAMs.

It applies unchanged in all three ChIP modes. A pair counts once whether one
or both mates overlap, as with `-p --countReadPairs -O`. A single-end read has
its own name. A singleton or chimeric pair in a `--proper-pair-off` run counts
once in both tools. One `CountCheck` job per BAM (`-n 2 -M 8G`,
`RATE_CCHECK=1.5`) runs beside Count. After both stages the control job runs
`checkCounts.sh` on the summary and every `atlasFragments.txt`, writes
`out/macs/peaks_raw_fcCounts.checks.txt`, and stops before DESEQ on any
failure, with the first FAIL line in `MESSAGE`.

`mergePeaksToSAF.sh` writes the 0-based `bedtools merge` start into the
1-based SAF without adding 1, so featureCounts counts one extra base at the
left edge of every peak. This is pre-existing, and fixing it would change the
counts. Both checks test the same intervals as featureCounts, so they are not
affected. Record it as an issue.
